# PocketPath project instructions

PocketPath helps Kavindu understand income, spending and savings goals. Older references call the product Kavindu Finance; use PocketPath in the app.

- Use Kotlin, Kotlin DSL, Compose and Material 3; no XML screen layouts. Keep one activity and Navigation Compose. Minimum SDK is 26; target SDK must remain 34 or higher. Preserve `com.pocketpath` as namespace and application ID.
- Work within the existing `app` module. Keep template tool versions unless a verified compatibility need requires a change. Manage pinned dependencies through `gradle/libs.versions.toml`; use Hilt with KSP for injection.
- Team-tested IDE: **Android Studio Quail 2 | 2026.1.2 Patch 1**, confirmed by Hithush; recommend matching it for first setup. Preserve Gradle 9.5.0, AGP 9.3.3, Kotlin 2.2.10, Hilt 2.60.1, KSP 2.3.10 and Firebase BoM 34.14.1. Use JDK 21 with the existing daemon criteria, compile SDK 36.1 and machine-local SDK settings. Do not independently accept build-tool/dependency upgrades. README.md is the ordered teammate setup guide.
- Use existing Firebase project `pocketpathfirebase`, default database and Android registration `com.pocketpath`; Email/Password Authentication is already configured. Teammates obtain matching `app/google-services.json` from Hithush or the existing registration, keep it ignored, and register separate app test users. Do not create another project/database/registration. Console membership is separate from app login. Hithush coordinates shared rules deployment; Git merging/builds do not deploy rules. New feature writes require coordinated rules/schema changes. Never share Google-account passwords or service-account private keys.
- `com.pocketpath`: Application and Activity entry points. `navigation`: shared typed routes and app shell. `ui.theme` and `ui.components`: reusable presentation. `di.FirebaseModule` provides real Firebase/authentication bindings; keep sample repositories out of production bindings.
- `feature.home`, `feature.activity`, `feature.plan`, `feature.goals`, `feature.transaction`, `feature.accounts`, `feature.settings`: feature screens and future feature ViewModels. Add `feature.income` and `feature.spending` when those flows arrive. Do not add empty layer classes.
- `domain.model`, `domain.money`, `domain.validation`, `domain.calculation` and `domain.repository` contain platform-neutral shared records, exact arithmetic, structural checks and contracts. `data.sample` is opt-in in-memory development code with no production Hilt binding. `data.repository` owns Firebase authentication and financial persistence, `data.firebase` owns mapping/UID paths, and `data.local` owns durable drafts/receipts/coverage. `feature.auth` and `feature.finance` coordinate authenticated presentation and session-scoped financial state. Composables render state and emit events; ViewModels expose immutable StateFlow and use coroutines for asynchronous work. Keep data access and financial calculations outside Composables.
- Sugeerthan owns Income and Accounts. Tharukshan owns Spending and Planning. Hithush owns Goals and Financial Overview. Coordinate shared model, repository and navigation changes across all three; Hithush coordinates integration.
- Financial amounts use shared Money/EntryAmount/CryptoQuantity types under the SRS: fiat Long minor units, LKR/USD scale 2, BigInteger crypto atomic units (78 digits, scale 0–18), exact BigDecimal rates and final HALF_UP historical LKR conversion. Reject excessive entered precision and check bounds/overflow; never use Float/Double. Keep native movements, report components and reservations separate. Unknown cost/profit stays explicitly unknown. Negative recorded balances produce warnings, not an expense-entry prohibition.
- The implemented P01 baseline includes authentication, UID-scoped Firebase repositories, LKR account/opening creation, initial categories, ordinary expenses, balances/Activity and device-local drafts/receipts with Firestore-managed offline expense writes. Plan/Goals and advanced financial/recurrence features remain deferred. Account creation requires online transactions and offline expenses require cached references. See `Docs/P01-Final-Handoff.md` for current integration agreements, verification evidence and security blockers; earlier block documents are historical.
- Coordinate new transaction kinds across codec, validation, calculations, rules and fixtures. Account/category editing and archival require repository operations, revision handling and rules changes; current rules deny updates. Preserve session cleanup, durable drafts, sync states and exact operation identity. Coordinate shared contracts/navigation before merging. Never automatically submit stored receipts during recovery; receipt inspection shares the submission mutex only through the handoff snapshot, not pending-write/server waits.
- Caller-retained operation IDs provide replay safety: identical retries must not post again; conflicting reuse fails. Production repositories enforce authenticated user scope and read-dependent rules. Runtime pending/cloud/cache metadata is not stored as editable proof on financial events. CompleteLedger and paginated ActivityPage are distinct; never derive full balances or summaries from a displayed page/incomplete cache.
- Before edits, inspect Git branch/status and preserve all existing staged, unstaged and untracked user changes. Do not reset, overwrite unrelated work, commit or push unless requested. Intended foundation branch: `feature/p01-foundation`.
- Build/check with the existing wrapper: `.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug --console=plain`; lint is optional when requested/tooling is available: `.\gradlew.bat :app:lintDebug --console=plain`. Use Android Studio's Gradle JDK (daemon criteria specify JDK 21). Keep current dependencies, including Firebase BoM 34.14.1. See `Docs/P01-Final-Handoff.md` for current results and remaining manual security checks; a commit/push is not evidence that a blocked check passed. App builds do not deploy rules; Firebase configuration/rules deployment requires separately authorized maintainer action.
- Keep SDK paths in ignored `local.properties` and machine configuration. Keep signing keys, passwords and service-account credentials local and ignored. Never commit credentials. Preserve wrapper scripts, properties and `gradle-wrapper.jar`.
